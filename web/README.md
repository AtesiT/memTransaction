# Транзакционная память — интерактивный стенд (веб-версия)

Лабораторная работа №1. Стенд показывает в реальном времени, как работает
**транзакционная память** и чем оптимистичный подход (CAS / STM) отличается от
пессимистичного (блокировки) и от «сломанного» варианта без синхронизации.

Демонстрация соответствует двум примерам из задания:

| Пример из задания | Что показывает стенд |
|---|---|
| **1. STM-механизм на чистом C# через CAS** (`Interlocked.CompareExchange`, 100 задач по +10) | вкладка **«Пример 1»**: потоков 2…16, каждый делает зачисления на счёт; видно конфликты CAS и повторы |
| **2. Транзакционный перевод между связанными объектами** (`Transactional<T>` + контекст транзакции) | вкладка **«Пример 2»**: переводы между 4 счетами, журнал чтения/записи, валидация версий, откат и повтор |

## Запуск

```bash
cd web
node server.js          # по умолчанию порт 8080
# затем открыть http://localhost:8080
```

Сервер нужен, потому что:

1. Web Workers не работают по схеме `file://`;
2. без заголовков `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`
   браузер запрещает `SharedArrayBuffer` — а это и есть «общая память» потоков.

Если открыть файл как `file://` или заголовки недоступны, стенд **не ломается**:
автоматически включается симулятор планировщика с тем же алгоритмом (об этом
честно сообщает индикатор в правом верхнем углу).

## Два режима исполнения — один и тот же алгоритм

```
        tm-core.js  (алгоритм: генераторы шагов + драйвер)
              │
     ┌────────┴─────────┐
     │                  │
 worker.js          sim-engine.js
 (настоящие потоки:  (кооперативный планировщик:
  Web Worker +        по одному шагу за такт,
  SharedArrayBuffer   порядок потоков перемешивается)
  + Atomics)
```

* **Настоящий режим** — честная параллельность: `Atomics.compareExchange` работает
  так же, как `Interlocked.CompareExchange` в C#. Конфликты возникают сами, от
  того что потоки физически выполняются одновременно.
* **Симулятор** — тот же код алгоритма, но планировщик модельный: он перемешивает
  порядок потоков и создаёт конфликты детерминированно. Нужен там, где
  `SharedArrayBuffer` недоступен.

Именно поэтому важно прогонять тесты **в обоих** режимах: часть гонок
(например, неатомарное чтение «значение + версия») воспроизводится только на
настоящих потоках.

## Что смотреть в интерфейсе

0. **Схема переводов** (главная картинка) — участники с балансами, соединённые
   линиями. По линии летит монетка с суммой:
   * зелёная долетела до получателя — транзакция зафиксирована, у получателя
     в этот же момент прибавились деньги;
   * красная погасла на полпути — конфликт версий: транзакция откатилась,
     деньги никуда не ушли и попытка повторится;
   * фиолетовая погасла у отправителя — недостаточно средств;
   * у участника горит «ждёт» — счёт занят пессимистичной блокировкой.
   В «Примере 1» схема другая: потоки-кружки вокруг счёта, и каждая монетка —
   успешно прошедший `CompareExchange`.

1. **Счета** — баланс, версия данных, признак блокировки. Версия — то, чем
   транзакция проверяет конфликт.
2. **Инвариант банка** —
   для переводов: сумма на счетах обязана оставаться неизменной;
   для зачислений: баланс обязан вырасти ровно на `10 × число операций`.
   В режиме «без синхронизации» инвариант ломается — это и есть демонстрация
   проблемы.
3. **Состояние потоков** — кто читает, кто считает, кто валидирует, кто ждёт
   блокировку.
4. **Таймлайн** — дорожка на каждый поток: рамка = одна попытка транзакции,
   внутри цветные фазы. Видно, как при STM потоки работают параллельно и лишь
   иногда «переигрывают» попытку, а при блокировках стоят в ожидании.
5. **Журнал выбранного потока** — локальный лог транзакции: что прочитано в
   read-set, что записано в write-set, прошла ли валидация.
6. **Показатели** — операции, коммиты, откаты-конфликты, отказы, скорость и
   эффективность (доля успешных фиксаций).

## Темп показа

В панели управления есть три готовых режима — их можно переключать на ходу,
не останавливая демонстрацию:

| Режим | Пауза между операциями | Работа в транзакции | Для чего |
|---|---|---|---|
| 🐢 **показ** | 420 мс | 1200 мкс | разобрать один перевод по шагам: видно чтение, вычисления, валидацию, коммит |
| ▶ **обычный** | 80 мс | 320 мкс | наблюдать общую картину, монетки и отказы |
| ⚡ **нагрузка** | 4 мс | 200 мкс | конкуренция: всплеск конфликтов и повторных попыток |

Ползунки ниже («работа внутри транзакции», «пауза между операциями») позволяют
настроить темп вручную. Чем больше «работа внутри транзакции» (аналог
`Thread.SpinWait`), тем чаще транзакции конфликтуют: это самый наглядный
способ показать, почему при высокой конкуренции оптимистичный подход
перезапускает транзакции.

## Проверка корректности

```bash
node tests/tm.test.js       # алгоритмы: инварианты в 10 сценариях + реальные потоки
node tests/network.test.js  # схема переводов: монетки, «в пути», конфликты, перегрузка
node tests/ui-smoke.js      # интерфейс: оба примера, режимы, темп, пауза, журнал
```

Тесты проверяют в том числе то, что «сломанные» режимы действительно ломаются
(иначе демонстрация была бы нечестной), а корректные — держат инвариант:

* CAS-зачисление: ни одно пополнение не потеряно, конфликтов — тысячи;
* STM-переводы: сумма на счетах неизменна, откатов-конфликтов — тысячи;
* STM + блокировки одновременно на общих данных: инвариант сохраняется;
* 16 потоков на 8 счетов — высокая конкуренция;
* те же проверки в `worker_threads` с `SharedArrayBuffer` и `Atomics`.

## Важные детали реализации (то, что обычно и ломается)

1. **Валидация и фиксация должны быть неделимы.** Если два потока успеют
   провалидироваться на одной версии данных, оба зафиксируют устаревшие
   значения. В стенде фиксация идёт через короткий критический участок
   (`commit-lock`) — так же поступают реальные STM-библиотеки (TL2 блокирует
   write-set).
2. **Чтение «значение + версия» должно быть согласованным** (приём seqlock:
   версия → значение → версия). Иначе транзакция запомнит старое значение с
   новой версией и пропустит конфликт.
3. **Смешение дисциплин синхронизации требует аккуратности.** Захват блокировки
   «пессимистичным» потоком выполняется под тем же критическим участком, а
   `CAS` не срабатывает на заблокированном счёте — иначе устаревшее значение
   затрёт зафиксированную транзакцию.
4. **Откат побочных эффектов невозможен.** Внутри транзакции нельзя писать в
   файл, отправлять письмо и т. п. — при конфликте это не «откатится».
5. **При высокой конкуренции STM перезапускает транзакции.** Это видно по
   счётчику откатов-конфликтов; защита от «живого» ожидания — ограничение
   числа повторов.
6. **Визуализация не врёт.** Баланс получателя увеличивается ровно тогда,
   когда монетка долетает (`network.js` хранит суммы «в пути»), а при конфликте
   не меняется ни один баланс — потому что откатилась вся транзакция.
