Что такое транзакционная память

При работе с общей памятью потокам нужна синхронизация. Классические способы: блокировки (mutex), алгоритмы без блокировок (lock-free, CAS) и транзакционная память.

Транзакционная память — технология синхронизации, которая объединяет группы инструкций в атомарные транзакции. Подход оптимистичный: мы считаем, что потоки редко трогают одни и те же данные, поэтому большинство транзакций проходит успешно. Если конфликт всё-таки возник — транзакция отменяется и обычно запускается заново (retry). Блокировки, наоборот, пессимистичны: всегда запрещают двум потокам быть в критической секции одновременно.

Как устроена транзакция

  1. Локальный журнал. Поток выполняет все операции внутри транзакции в изолированном пространстве: чтения запоминаются в read-set вместе с версией данных, записи попадают в write-set. Остальные потоки изменений не видят.
  2. Валидация. При завершении система проверяет, не изменил ли кто-то те ячейки, которые транзакция читала (сравниваются версии).
  3. Коммит или откат. Конфликтов нет — write-set применяется к общей памяти целиком. Есть конфликт — откат и повтор.

Плюсы и минусы

  • простота: целые методы заворачиваются в блок транзакции;
  • нет блокировок — нет взаимных блокировок (deadlock);
  • выше уровень параллелизма и производительность при редких конфликтах.
  • при высокой конкуренции потоки много раз перезапускаются (нагрузка на CPU);
  • нельзя выполнять необратимые операции (письмо, отправка e-mail, запись в файл);
  • сложнее отлаживать, накладные расходы на журналы.

Что именно происходит на этом стенде

Стенд повторяет цепочку из лекции: чтение → локальный журнал → валидация версий → коммит или откат с повтором. Важная деталь, которую видно только в реальных потоках: валидация и фиксация должны быть неделимы (в настоящих STM для этого блокируется write-set). Иначе два потока успевают провалидироваться на одной версии и оба записывают устаревшие данные — инвариант банка ломается. Здесь фиксация идёт через короткий критический участок, а чтение использует приём seqlock (версия → значение → версия).

Почему в .NET нет STM «из коробки»

В официальном рантайме .NET транзакционной памяти нет: Microsoft закрыла экспериментальный проект MSR STM.NET. Поэтому в задании используются два практических варианта:

  1. Оптимистичная блокировка через CAS — Interlocked.CompareExchange. Это самый близкий аналог STM «из коробки» для простых типов (Пример 1).
  2. Своя мини-STM — транзакционные переменные Transactional<T> плюс менеджер транзакций с журналом, валидацией и повтором (Пример 2). Именно так работают библиотеки вроде Nito.Transactions.

Производительность и побочные эффекты

Откат побочных эффектов невозможен: если внутри транзакции отправить письмо или записать лог, при конфликте это не «откатится». Плюс ведение журналов даёт нагрузку на память и сборщик мусора. Поэтому в реальных .NET-проектах чаще берут ConcurrentDictionary, каналы System.Threading.Channels или модель акторов, а STM применяют точечно — там, где нужны атомарные изменения нескольких связанных объектов.

Пример 1 из задания: STM-подобное изменение через CAS

Полный аналог кода задания — безопасное изменение баланса без lock, через оптимистичную блокировку и повтор при конфликте.

class Account
{
    private int _balance;                 // общая память: меняется только атомарно
    public int Balance => Volatile.Read(ref _balance);

    public void DepositTransactional(int amount)
    {
        int currentBalance, newBalance;
        do
        {
            // 1. «Начало транзакции»: читаем текущее состояние
            currentBalance = Volatile.Read(ref _balance);

            // 2. Вычисляем новое значение локально
            newBalance = currentBalance + amount;

            // Имитация тяжёлой работы / возможного переключения контекста
            Thread.SpinWait(10);

            // 3. Пытаемся зафиксировать (commit).
            //    CompareExchange атомарно проверит: _balance всё ещё равен
            //    currentBalance? Если да — запишет newBalance и вернёт старое
            //    значение; если нет — вернёт то, что успел записать другой поток.
        }
        // Если вернулось НЕ currentBalance — транзакция «откатывается»
        // и цикл идёт на новый круг (retry).
        while (Interlocked.CompareExchange(ref _balance, newBalance, currentBalance) != currentBalance);
    }
}

class Program
{
    static async Task Main()
    {
        var account = new Account();
        Task[] tasks = new Task[100];
        for (int i = 0; i < tasks.Length; i++)
            tasks[i] = Task.Run(() => account.DepositTransactional(10));

        await Task.WhenAll(tasks);
        Console.WriteLine($"Итоговый баланс: {account.Balance}");   // всегда 1000
    }
}

Пример 2 из задания: своя STM для связанных объектов

Одной CAS-операции мало: перевод затрагивает два счёта, и нужно, чтобы изменение обоих произошло атомарно. Ниже — минимальная транзакционная память: транзакционные переменные с версиями, контекст транзакции с журналом чтения/записи, валидация и повтор.

// Транзакционная переменная: значение + версия для проверки конфликтов
public sealed class Transactional<T>
{
    private T _value;
    internal long Version;                       // «штамп» версии данных
    public Transactional(T value) { _value = value; Version = 1; }

    public T Read()                              // чтение внутри транзакции
    {
        TxContext.Current?.LogRead(this, Version);
        return _value;
    }
    public void Write(T value)                   // запись только в журнал
    {
        TxContext.Current?.LogWrite(this, value);
    }
    internal T RawValue => _value;
    internal void CommitValue(T value) { _value = value; Interlocked.Increment(ref Version); }
}

// Контекст транзакции: локальный журнал потока + фиксация
public sealed class TxContext
{
    [ThreadStatic] private static TxContext _current;
    public static TxContext Current => _current;

    private readonly Dictionary<object, long> _readSet = new();
    private readonly Dictionary<object, object> _writeSet = new();
    private static readonly object CommitLatch = new();   // фиксация неделима

    public static void ExecuteInTransaction(Action body, int maxRetries = 100)
    {
        for (int attempt = 1; ; attempt++)
        {
            var ctx = new TxContext();
            _current = ctx;
            body();                                   // операции пишутся в журнал

            lock (CommitLatch)                        // короткий критический участок
            {
                if (ctx.Validate())                   // никого не обогнали?
                {
                    ctx.Apply();
                    return;                           // успешная фиксация
                }
            }
            if (attempt >= maxRetries)
                throw new InvalidOperationException("Слишком много конфликтов");
            // иначе — откат и повтор целиком
        }
    }

    private bool Validate()
    {
        foreach (var kv in _readSet)
            if (VersionOf(kv.Key) != kv.Value) return false;
        return true;
    }
    private void Apply()
    {
        foreach (var kv in _writeSet) SetValue(kv.Key, kv.Value);
        _writeSet.Clear(); _readSet.Clear();
    }
}

public class BankModel
{
    public Transactional<int> AccountA = new(100);
    public Transactional<int> AccountB = new(50);

    public void Transfer(int amount) =>
        TxContext.ExecuteInTransaction(() =>
        {
            if (AccountA.Read() < amount) throw new InvalidOperationException("Недостаточно средств");
            AccountA.Write(AccountA.Read() - amount);
            AccountB.Write(AccountB.Read() + amount);
        });
}

Как проверить корректность механизма

Стенд можно проверить автоматическими тестами — они гоняют ту же самую логику (js/tm-core.js) без браузера, включая настоящую параллельность (worker_threads + SharedArrayBuffer + Atomics):

cd web
node tests/tm.test.js

Что именно проверяется:

  • CAS-зачисление: ни одно пополнение не потеряно, конфликтов много;
  • зачисление без синхронизации: обновления теряются (демонстрация проблемы);
  • STM-переводы: сумма на счетах неизменна (инвариант банка);
  • переводы без синхронизации: инвариант нарушается;
  • STM + блокировки одновременно на общих данных: инвариант сохраняется;
  • высокая конкуренция: 16 потоков на 8 счетов;
  • и то же самое в реальных параллельных потоках — там ловятся гонки, которые симулятор принципиально не воспроизводит.

Границы применимости

Транзакция не должна выполнять необратимые действия (запись файла, отправка письма): при откате их не «откатить». В реальных проектах .NET для таких задач применяют Event Sourcing / Sagas, а не STM.

Стенд повторяет схему из задания: CAS-цикл (Пример 1) и транзакционная память с журналом и валидацией (Пример 2). Данные — js/tm-core.js.
